# Anti-Overengineering

## 用途
防止 Codex 对小项目进行过度设计。
**专业不是堆架构，而是符合项目规模。**

## 使用场景
- 每次开始新项目前
- Codex 想加微服务/消息队列/复杂架构时
- 发现项目设计超出了需求规模时

## 核心原则

### 1. 小项目不要微服务
> 一个仓库、一个项目文件夹、一条 npm install 就能跑。

如果一个项目只有：
- 不到 10 个页面
- 不到 10 张表
- 不到 5 个 API 端点
- 单一团队开发

那就**绝对不要**拆成微服务。

### 2. 第一版不要的复杂组件
| 组件 | 什么时候才需要 |
|------|---------------|
| 消息队列 | 日均处理 > 10万条异步任务 |
| 多租户 | SaaS 明确要求隔开不同客户数据 |
| 复杂 AI 管道 | AI 工具确实有复杂后处理流程 |
| 复杂支付 | 需要分账/退款/对账时 |
| 工作流引擎 | 审批流程超过 5 步 |
| WebSocket | 需要实时双向通信时 |
| Redis 缓存 | 数据库 QPS > 1000 时 |
| Docker | 需要多环境一致部署时 |
| Kubernetes | 需要管理多个容器时 |

### 3. 第一版不要加的复杂度
- ❌ GraphQL（REST 足够）
- ❌ tRPC（过度抽象）
- ❌ Nx/Turborepo Monorepo（单项目不需要）
- ❌ 国际化框架（先做中文）
- ❌ 暗黑模式（第一版只做亮色）
- ❌ 自定义 CLI 工具
- ❌ 复杂的 CI/CD Pipeline
- ❌ 自动化 E2E 测试（先做 smoke test）

### 4. 判断是否过度设计的标准
问自己三个问题：
1. 这个功能/组件是用户第一版**必须用到的**吗？
2. 没有它，用户能不能完成核心目标？
3. 加上它，项目复杂度增加多少？

如果第一个答案是"否"→ 不要加。

### 5. 何时可以加复杂度
- 用户明确说"要做微服务架构"
- 第一版已经稳定运行，确实需要扩展
- 数据量确实达到了瓶颈
- 团队确实需要这些组件

## 专业的标准
- ✅ 专业 = 选择了合适的复杂度
- ✅ 专业 = 项目能用最简单的方式运行
- ✅ 专业 = 代码清晰、有约束、有状态处理
- ❌ 专业 ≠ 堆砌架构组件
- ❌ 专业 ≠ 用了"大公司才用"的技术

## 常见错误
- ❌ 一个 CRUD 后台拆成 3 个微服务
- ❌ 一个展示网站用 Next.js SSR + GraphQL + Redis
- ❌ 一个表单工具加 Kafka 消息队列
- ❌ 用户说"做个页面"→ 建了全栈项目 + 数据库 + Auth

## 输出格式（需要时）
```
## 过度设计检查

### 当前方案
- [组件/架构]：[理由]

### 建议简化
- 去掉：[组件]
- 原因：[项目规模不需要]
- 替代方案：[简单方案]
```
