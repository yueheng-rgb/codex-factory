## 1 项目类型

现有本地开发者工具与Agent控制平面。Router七类中没有精确匹配，不强行归入带计费的SaaS或新建HTTP服务。项目体量M，状态一致性与执行副作用风险高；本轮为现有系统的有限扩展。

## 2 推荐架构

沿用 `packages/factory-cli` 的TypeScript / Node.js 24单进程CLI架构，以及现有SQLite上下文和知识存储。任务图、派发与验收仍遵循现有文件合同，不在第一阶段迁移全部运行状态到数据库。

复用已有文件锁、原子文件替换、路径校验、哈希与独立验收。文件锁和单文件原子替换不等于跨文件事务；新接口必须检测不完整写入，并拒绝把残缺状态当成成功。

## 3 资源选择

- Starter：现有 `packages/factory-cli`，不重新脚手架。
- Blueprint：现有README、类型定义、编排和证据模块的合同；保留当前CLI风格。
- Skills：`project-expertise-flow`、`integration-failure-patterns`；结合现有任务和权限校验模式。
- 研究侧读取官方事务、持久化与幂等资料。仅借鉴设计原则，不因此引入LangGraph、向量数据库或新的运行时依赖。

## 4 用户角色与核心路径

使用者是本地项目维护者；主控制器负责派发和受控修复；Implementer只能提交工作结果；Verifier独立验收，不能通过修改被测实现让自己通过。

核心路径：执行现有任务 → Verifier判定失败 → 用户查看失败原因与证据 → 创建有次数限制且关联原失败的新修复run → 复用原生派发机制 → 独立重新验收 → 同时查看旧失败与新结果。

## 5 命令结构

没有新增Web页面。以下为拟新增CLI合同，名称在实现前按现有解析模式核对：

| 命令 | 用途 | 行为边界 |
| --- | --- | --- |
| `factoryctl run inspect --run <id> --json` | 汇总任务、派发、验收、失败原因和证据路径 | 只读；不追加上下文、不刷新状态、不自动派发 |
| `factoryctl repair create --from-run <id> --task <id> --tasks <file> --request-id <id> --json` | 基于已验证的失败证据建立修复run | 持久化关联及有界修复计划，不直接启动外部Agent |
| 现有 `factoryctl plan --run <id> --json` | 继续合法run的计划流程 | 不冒充只读查看命令；保持其已有写入行为 |
| 现有派发、handoff、verify命令 | 执行并独立验收 | 保留原合同，补充相关回归测试 |

`inspect`成功读取到FAILED运行本身不是读取错误：在JSON中分别表达读取结果与运行结果。文件损坏、证据不匹配或错误参数应非零退出，且禁止乐观生成总体PASS。

## 6 接口草图

内部新增接口优先保持小而明确，复用现有读写函数。拟定：

- `inspectRun(projectRoot, runId)`：返回schema版本、run标识、完整性结果、任务状态、阻塞原因、证据引用、已知限制与建议行动。对当前宿主进程状态无法核实时明确为unknown。
- `createRepairRun(projectRoot, request)`：输入父run、失败task、修复任务草稿、幂等请求标识；输出新run、关联摘要、修复次数、下一条现有命令。与已有请求完全一致时返回相同结果；同ID不同输入必须拒绝。
- 收紧 `setRunTaskStatus`：调查调用者后，禁止已验收失败任务直接回到pending/ready。原状态同值重试继续幂等；blocked等非终态转换需独立判断，不能机械全部锁死。

错误至少区分：run/task不存在、来源不是可修复的失败、证据损坏、仍有活动或状态不明的执行、次数超限、同请求参数冲突、范围扩张、部分创建残留。

## 7 数据草图

沿用 `Project → Run → Task → Assignment → Handoff → VerificationReceipt`。

新增修复关联记录最少包括：schema版本、根run、父run、原失败task、父验收回执路径及摘要、新run、request-id、请求摘要、创建与更新时间、修复序号和上限。具体字段名与目录遵循现有JSON命名风格。

同一修复链上限默认2次，由已批准配置统一控制，不能每次生成新run就重置计数。同请求唯一性、同父任务的并发修复冲突在项目级锁下校验。原失败run的任务图、handoff和验收回执保持不变；关联记录独立保存。

第一阶段不需要新数据库表。创建跨多个文件时，使用明确的准备与提交状态；读取端不能接受未提交的新run。中断留下残留时报告原因和受控恢复步骤，不擅自清理或启动任务。是否能复用现有文件提交机制，由故障注入结果决定；不宣称掉电级耐久性。

## 8 权限边界

- 控制平面校验路径、任务身份、来源回执、幂等参数、修复次数和scope，不只依赖提示词。
- Worker无权给自己标记verified，Verifier不能修改被验收实现。
- 修复任务默认不得扩大原批准write_scope，原业务验收标准不能削弱；真正改变需求需新的设计确认。
- 活动Agent或执行状态不明时不自动重派，不把超时等同于外部副作用未发生。
- 当前scope_guard不是OS级隔离。同权限恶意进程能够修改控制文件的问题，不在本轮伪装成已解决。

## 9 完整性清单

- 状态转换有明确的正向、拒绝及幂等测试。
- 查看命令只读、有JSON合同、有失败原因，不把模型自述当作完成。
- 修复创建验证父回执、保留来源、限制次数与scope、防止重复创建。
- 错误信息包含可执行下一步，敏感值不进入输出。
- 旧run证据不可覆盖；部分创建和损坏文件不能被视为成功。
- README有构建、演示和限制说明；新增测试接入现有CI。

## 10 最容易出错的十处

1. 允许failed重新排队，导致失败证据与当前状态不一致。预防：明确终态语义及调用路径回归。
2. `inspect`调用有副作用的`plan`，查看即改状态。预防：只复用纯读取函数并比较前后文件摘要。
3. 判断修复资格时只读status，不校验独立验收回执。预防：同时校验回执来源和绑定。
4. 重试创建生成多个修复run。预防：持久化请求摘要与唯一性检查。
5. 每个新run重新计算次数，绕过上限。预防：校验完整修复链及并发分支。
6. 只修改一个JSON就声称跨文件状态已经一致。预防：准备/提交状态与中断点测试。
7. 超时后原Agent仍运行，重派导致两次写入。预防：不自动重派不明执行。
8. 修复草稿扩大scope或删除困难的验收条件。预防：与原批准合同比较，变化需确认。
9. 只验证新结果，旧run或其他task证据被覆盖。预防：前后摘要与隔离测试。
10. 本地假回执测试被写成真实Agent或远程CI结果。预防：报告中分别记录离线测试、真实试验与远程结果。

## 11 第一阶段最小闭环

一个受控示例任务，独立验收故意失败；用inspect看到明确原因；用repair create创建唯一且有来源关联的新run；使用现有执行和验证接口完成修复；旧失败证据仍可查看。

分两步实施：先做只读诊断与终态一致性，再做有界修复创建与完整演示。Windows本地先验收；跨平台CI若可运行则绑定当前提交结果，否则明确未运行。暂不新增Dashboard、混合检索、自动失联重派、远程模型服务、支付、微服务或全量持久化迁移。

## 12 必须验证的真实用户路径

1. 用户查看成功、失败、阻塞的既有run，得到不同且正确的状态与下一步；查看前后文件内容不变。
2. 用户查看损坏或缺少回执的run，看到非零错误，而不是成功摘要。
3. 失败任务不能通过底层接口或已有命令被原地复活为可执行任务。
4. 用户从有效失败创建修复run，原run文件内容保持不变，新run追溯到原回执。
5. 同一创建请求重复提交返回同一个新run；同请求不同输入拒绝；并发请求不突破限制。
6. 修复次数超限、scope扩大、验收条件削弱、状态不明的活动任务都被拒绝。
7. 创建期间注入中断后，不会出现可被正常执行的半成品run；重新查看能解释残留状态。
8. 一次完整的修复和独立重新验收，保留旧FAIL与新结果；模拟宿主测试和真实宿主演示明确分开。

实施验证命令：在 `packages/factory-cli` 执行 `npm run typecheck`、`npm test`、`npm run build`、适用的CLI烟雾测试。当前只执行了前两项基线；未执行本设计的新增验收路径。
