# Factory 能力与增益评测方案

状态：方案，尚未执行。目标不是保证测出正提升，而是在有限预算内区分能力、实际增益和额外开销。

## 1. 需要回答的问题

1. 相同模型、相同输入资料、相同预算下，Factory 是否比普通 Agent 更容易完成合格交付？
2. 结果对比澄清、经验选择性复用、假设驱动诊断，相比仅有编排和验证的 Factory 是否有增益？
3. 增益体现为结果更正确、少返工、少人工解释，还是只是更多流程？
4. 哪些任务不值得启用这些能力？

旧 demo 是公开合成小例子的流程验证，不进入新评测的未见任务分母。已有经验筛选词面夹具也仅用于开发校准。

## 2. 三组配对对照

| 组 | 配置 | 比较目的 |
| --- | --- | --- |
| A：普通 Agent | 同一模型，正常代码工具、原始需求、历史记录及文档；允许自然提问、检索、自测和修复，不附加 Factory | 产品整体对照 |
| B：Factory 基础流程 | 保留现有任务契约、编排、作用域、独立验证；不调用结构化澄清、教学经验注入和假设诊断模块 | 当前版本的消融组，不冒充历史原版 |
| C：Factory 新增能力 | 与 B 相同基础，加本任务适用的新模块，不强制每题启用所有模块 | C 对 B 观察新增能力组合的边际效果 |

三组必须使用同一模型版本、推理设置、代码快照、工具可用性和原始事实材料。A/B 也可主动读历史材料并自行总结，不能只给 C 关键答案。
两组 Factory 的内部 Verifier 成本计入各自预算；外部统一评分器不向任何组反馈，也不算产品推理成本，单列评测开销。
C-B 是能力组合的消融，不足以精确分解每个模块的因果贡献；定向题的轨迹只能辅助解释，精确归因需要之后的单模块对照。
运行适配器选择调用路径，不假设项目已有不存在的全局功能开关，也不为制造 B 组改动生产实现。

## 3. 六个冻结任务

使用一个小型离线“订单导入与对账”代码仓库。建议 8-12 个源文件、3 个模块、纯 Node/TypeScript，无数据库、UI、付费接口或新依赖。每题独立还原同一合法起始快照，不串联上一题的结果。
这里是业务任务设计，具体接口与实现须在任务包冻结时确定；不是重新开发一套评测平台。

| 题 | 工作请求 | 主要观察 |
| --- | --- | --- |
| T1 决策澄清 | 合并重复订单，但初始需求未说明哪条优先；模拟业务方有事先冻结的规则 | 是否发现重要歧义、问题是否易答、确认后是否仍实现错误、用户交互轮次 |
| T2 经验迁移 | 将历史上已经纠正的项目专属导入约定应用到另一供应商适配器，换字段与样例 | 同一历史信息在三组均可访问，是否少重复同类错误，检索和注入成本如何 |
| T3 换说法迁移 | 同一类经验换一种业务表述，保留可推断但不重叠的关键措辞 | 现有词面召回是否漏选；完整任务最终能否被解决，而非只看候选数 |
| T4 经验不适用 | 新的严格接口不能沿用历史宽松导入规则，当前规范明确优先 | 是否误用经验、引入本来没有的缺陷；无害性是硬条件 |
| T5 故障定位 | 相同错误表象可能来自读取、转换或汇总层；提供可复现数据与只读诊断命令 | 第一次改动是否针对真实原因、无关修改与试错次数、修复后是否回归 |
| T6 普通修改 | 明确要求新增一个汇总字段，数据规则与接口均完整 | 普通任务是否因 Factory 多花明显成本；不要只挑 Factory 擅长的题 |

T1 使用事先固定的模拟业务回复规则，三组均可询问；任意自然语言只要问到相同语义就得到同样事实，不要求 Factory 专有格式。未获偏好时可以正确报告待确认，不把谨慎阻塞混同错误交付，但交付成功单独计数。
T2/T3 的历史修正与后续目标分离，不提供目标解法；C 的 Skill 形成、审批和读取成本需记录。若使用预置经验，必须标为预置，并与现场学习分开报告。所有业务回复与数据标为合成，不冒充真实客户事件。
T5 的缺陷为预先注入的诊断夹具，同样提供给三组；只能证明受控故障下的定位表现，不能归入自然开发出错率。

## 4. 统一评分，不让 Factory 给自己打分

- 冻结输入、需求、用户回复规则、公开测试、外部验收及预算，再开始模型运行。先用人工参考实现验证题目可解。
- 每题评分以实际代码结果为准：需求正确、公开与未展示的验收通过、既有行为不回归。未展示测试只能检验可获知规范，不偷偷新增要求。
- 最终验收由主控在交付后独立执行；测试文件和参考答案不放入受测 Agent 可用的任务材料。仅有提示词禁止读取不能宣称系统级隔离，任何泄漏须标记该次污染。
- 正确、错误、待确认、超预算、宿主失败分别记录，所有开始的尝试都列出。不能删除失败后只保留成功重跑。
- Agent 自报成功、Factory 自身 PASS/FAIL、外部实际交付判定分别保留，观察误报成功及误拒正确交付。现有“所有非零命令均判失败”的规则不能在评测中偷偷放宽。
- 不因使用了特定工具、生成多少文档或猜中了固定补丁文本而加分；合法的不同实现同样通过。

## 5. 指标与预算

主要指标：每组外部验收成功数/完整尝试数；逐题列出 A/B/C 的配对胜、平、负，不把几十条断言当几十个独立任务。
辅助指标：第一次提交结果、内部返工轮数、真实业务问答轮次、已确认需求仍出错次数、重复历史错误、误用经验、无关文件改动、误报 PASS、误拒合格交付。

正式运行前锁定统一预算：建议每题每组最多 20 分钟活跃执行窗口，至多 2 轮实现/修复；Worker 与内部 Verifier 共享窗口，不能各自获得一份预算。额度等待、用户等待和主控调度间隔单列，不伪装成推理耗时。

2026-09-13 实现补充：目前宿主无法提供完整活跃执行计时，因此新增适配器采用更保守的 **20 分钟连续墙钟窗口**，从首次派发准入开始，包含控制器调度、额度等待和内部验证，不暂停扣时；两轮指初次实现加一次修复。该口径只用于后续新运行，不能补写进已完成试跑。经验建立和任务准备若在准入前进行，仍须另列成本。控制器暂停时不能独立强杀宿主 Agent，因此当前是控制器协作式限额，非硬实时上限；超时及未确认停止必须保留记录，不能算作预算内完成。正式冻结时三组统一采用此口径。
有真实用量时报告全部参与 Agent 的输入/输出 Token、费用；失败和内部验证也计入。每次合格交付成本=整组全部尝试成本/成功交付数，零成功时不计算有限值。
拿不到逐次用量就标为未知，仅报可观察的调用数、上下文字节、返工及分段时长，不把它们折算成“实际费用下降”。没有可靠计时数据同样标未知。
经验复用同时报首次建立成本和后续使用成本，不能把初始化免费化；也不凭假定未来复用次数摊薄实测成本。
不合成一个可调权重的“综合好分数”：分别展示质量与成本。如果质量升而成本也升，明确报告取舍。

## 6. 三阶段，限制规模

第一阶段：制作并校准任务包。选 T1、T2 的开发变体，A/B/C 各一次，共 6 次任务尝试，检查难度、评分和证据可用性；只算开发试跑，不报告正式成功率。
若基线已全对，不通过删除基线优势题或追加陷阱追求正差异。若任务过易/不合理，只能在正式冻结前对所有组统一修订，并保留开发记录。

第二阶段：冻结六个新变体，A/B/C 各运行一次，共 18 次正式任务尝试。各题三组顺序轮换，干净上下文、独立工作目录，全部结果必须列出。18 是任务尝试数，不是 Agent 数；B/C 的独立验证会产生额外调用。
这是小样本方向性评测，不是统计稳定的泛化成功率。它能发现显著无用/有害模式，并给出可复查的配对结果。

第三阶段：先做决策，不默认扩充测试。全部打平且 C 更贵则收缩默认启用范围；只在某类任务受益则按类启用；若需公开宣称稳定提升，再另行批准整套预注册重复与未见变体，不只重跑赢的题。

本方案本身不派发 Agent，不启动 24 次尝试；先确认开发试跑的预算，再执行第一阶段。

## 7. 交付物与允许的结论

产物限定为任务包、轻量运行适配、逐题结果表和一页结论。复用现有 evals、原生派发及回执逻辑，不建后台、评分平台或持续审计系统。
能力轨迹可证明“完成过澄清到代码的闭环”“在未见变体上正确迁移经验”“反例中没有误用”“定位了注入故障”；对比表才能支持预算条件下的相对增益。
允许出现负结果。最终价值可能是少让用户反复解释、更少错误交付或可追溯决策，而非必然提升写代码能力。
